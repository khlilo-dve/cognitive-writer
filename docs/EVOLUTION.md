# Cognitive Writer — 演进史与设计理念

> 从 CLI 工具到对话式写作 Agent 的完整旅程。2026 年 7 月。

## 二、各版本关键变化

### v2.0 → v2.1：工程化

v2.0 是一个能用的原型——893 行单文件，`generate` + `learn` 两个子命令，骨架-渲染双通道 LLM 架构。但它的问题是典型的原型病：所有代码堆在 `main.rs`，错误用裸 String 传播，剪贴板注入中文乱码，没有测试。

v2.1 做了减法而不是加法——把 893 行单文件拆成 6 个模块：

```
main.rs (893 行, 上帝函数)
    ↓
main.rs + error.rs + llm.rs + clipboard.rs + io.rs + refine.rs
```

核心原则：**先建约束，再写代码。** 引入 `thiserror` 强类型 `AppError`，引入 `with_retry` 泛型重试消除三处重复，引入 36 个单元测试。剪贴板中文编码问题用 CF_HTML 字节偏移 + PowerShell MemoryStream 绕过 .NET UTF-16 转换解决。新增 `update` 子命令（整文重写）和 `--no-clipboard` flag。

版本号从 2.0.2 跳到 2.1.0，因为模块化重构本身就是一次架构升级。

---

### v2.1 → v3.0：从工具到 Agent

这是最根本的一次范式转移。

**v2.1 的设计假设：** 用户知道要什么，通过 CLI 子命令精确指定。
**v3.0 的设计假设：** 用户有模糊意图，Agent 负责理解、拆解、引导、执行。

具体变化：

#### 1. 交互模式：CLI → REPL

```
# v2.1
$ cargo run -- generate --input my_topic.md
$ cargo run -- learn https://...
$ cargo run -- refine article.md

# v3.0
$ cargo run
> 写一篇关于认知偏差的文章，轻辩风格
> OK
> 发布
```

命令变成了对话。用户不需要知道子命令、参数名、文件路径。

#### 2. 意图理解：关键词 → LLM 分类

v3.0 最初用纯关键词匹配做意图解析——找"写一篇"、"用"、"风格"这些硬编码字眼。这很快暴露了问题：自然语言不按规则来。"帮我整一篇认知偏差的，犀利点"这种表达关键词匹配直接失败。

修复方向很明确：**Agent 的核心是 LLM 理解 + 工具调用。** `classify_intent()` 用一个极小的 LLM prompt（~200 tokens）将自然语言分类为结构化 Intent，关键词匹配退化为 LLM 失败时的 fallback。"OK"、"取消"这类高频短指令走 0 成本快速预检，不调 LLM。

#### 3. 对话状态机

四个状态的有限状态机驱动整个交互流程：

```
Idle → WaitingForFulltext → WaitingForPublish → Idle
```

状态决定什么输入有效：在 Idle 下"OK"没有意义，在 WaitingForPublish 下"加个分论点"也没有意义。状态机是一个防御层——它阻止了用户和 Agent 之间的误解。

#### 4. 双平台发布

v2.1 只有剪贴板注入（手动粘贴到微信）。v3.0 增加了个人网站（Next.js + MDX + git push → Vercel 部署）。两个平台共享同一个检查点流程：

```
全文确认 → 剪贴板注入 + MDX 草稿写入 → 等待发布
发布 → git push (网站) + 提示手动粘贴 (公众号)
```

设计原则：**草稿和发布是两步，中间用户可以反悔。** 写 MDX 文件只是本地操作，git push 才是真正的"上线"。

#### 5. 主模块拆分

v3.0 将 main.rs 从 667 行进一步精简到 100 行，新模块各司其职：

```
main.rs (100 行) — 启动分流
repl.rs (1116 行) — 循环 + 状态机
intent.rs (894 行) — 意图解析
generate.rs / learn.rs / update.rs / refine.rs — 功能模块
website.rs / styles.rs — 新增能力
```

最终 14 个源文件，132 个单元测试，main.rs 从 893 行一路降到 100 行。

### v3.0 → v3.1：健壮性

v3.0 的 REPL 循环有一个根本问题：stdin 是阻塞读。进程死 = 全部状态丢失。你写了一篇文章，确认了大纲，到了全文确认阶段，终端关了——什么都没有了。

v3.1 做了两件事：

**1. 异步 stdin + 信号监听**

```
v3.0: stdin.read_line() ← 阻塞
v3.1: tokio::select! { stdin.next_line(), ctrl_c } ← 不阻塞
```

`tokio::select!` 让事件循环同时等待用户输入和系统信号。Ctrl+C 不再硬杀进程，而是触发 `save()` → 安全退出。

**2. 会话持久化**

`Repl` 结构体加上 `Serialize + Deserialize`，每次 `dispatch()` 后自动写 `~/.cognitive-writer/current.json`。启动时检测到文件 → 提示恢复。正常走完全流程 → 清除文件。

设计原则：**随时中断，随时恢复。** 这是长连接思想的正确落地方式——不加网络层，不加多会话，只做实打实解决了"进程死了怎么办"这个问题。

---

### 流程精简：3 检查点 → 2 检查点

v3.0 的一个过度设计被修正：大纲确认这个检查点被砍掉。

```
之前: 选题 → 大纲 →【等确认】→ 全文 →【等确认】→ 草稿 →【等确认】→ 发布
现在: 选题 → 大纲→全文一气呵成 →【等确认】→ 草稿 →【等确认】→ 发布
```

理由很简单：大纲 LLM 生成质量稳定后，不需要每步都等确认。用户已经描述了选题意图，再确认一个中间产物是多余的摩擦。人在看到完整文章时做的判断比在大纲阶段做的判断更准确。

## 三、设计理念

### 1. 人对人，不是人对工具

这是 v3.0 最根本的设计决策。用户不应该学习命令语法，不应该记忆子命令名称。Agent 的工作方式是：

> 你说什么 → 我理解 → 我执行 → 我汇报 → 你确认 → 我继续

就像你和一个会写文章的同事说话。这也是为什么意图理解必须走 LLM——规则引擎永远跟不上自然语言的多样性。

### 2. 渐进确认，不要一次全对

全文生成后用户可能想改第三段。发布前用户可能反悔。所以流程被拆成两个检查点：

- 全文确认：可以局部改、可以换风格、可以取消
- 发布确认：可以只发网站、可以只发公众号、可以暂缓

每一步都给了反悔空间。**用户不需要在开始就想清楚所有细节，Agent 在过程中帮你迭代。**

### 3. 进程不是边界，状态才是

v3.1 的核心洞察：不要因为进程会死就加复杂的基础设施（HTTP API、数据库、Redis）。一个 JSON 文件就够了。

`Repl` 结构体就是全部状态。序列化它。反序列化它。进程启动时检测它。进程结束时写入它。

### 4. 先做减法，再做加法

v2.0 到 v2.1：不是加功能，是拆模块、加测试、统错误处理。
v3.0：不是加花哨 UI，是把交互模型从命令翻成对话。
v3.1：不是加网络层，是把 stdin 从阻塞改成异步加个文件持久化。

每一次都是先让已有的东西更健壮，再往上加新东西。

### 5. 约束先行

项目从一开始就遵守一个铁律：**新项目先写 CLAUDE.md，新目录先定结构约定。** 所以有了 `ARCHITECTURE.md` 的先写再改、`Cargo test` 的每次必跑、`git commit` 的每版必记。132 个测试不是后来补的——是每次改动时不倒退的底线。

## 四、代码量演变

```
v2.0:  1 文件,  ~893 行, 0 测试
v2.1:  6 文件,  ~900 行, 36 测试
v3.0: 14 文件, ~4224 行, 124 测试
v3.1: 14 文件, ~4500 行, 132 测试
```

行数增长了 5 倍，但 main.rs 从 893 行降到了 126 行。核心复杂度从"一个上帝函数"变成了"14 个职责单一的模块 + 一个 REPL 编排层"。

## 五、当前能力边界

### 覆盖

- 自然语言 → 结构化意图（LLM 分类）
- 风格逆向学习（URL → 10 维度分析 → 风格文件）
- 文章生成（骨架→渲染双通道 LLM）
- 局部重绘 / 全文重写 / 换风格
- 双平台输出（剪贴板微信 + MDX 网站）
- 风格库管理（模糊匹配 / 列表 / 删除）
- 对话状态机（2 检查点 + 状态校验）
- 会话持久化（自动保存 + 恢复）
- 异步事件循环（stdin + 信号不阻塞）
- CLI 快捷模式（向后兼容）

### 不覆盖

- 选题推荐。用户带着意图来，Agent 不替用户做主。
- 多轮闲聊。每轮对话都有明确的任务意图。
- 数据统计、定时发布、Web UI、多平台分发。
- 英文版本同步生成。
- 微信公众号 API 集成（个人订阅号无权限）。
