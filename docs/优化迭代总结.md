# cognitive-writer 优化迭代总结（2026-08-13）

> 本 session 完成了风格 spec 化、状态机意图理解增强、风格名拼音归一化匹配三项改造。
> 这份文档是「接下来该优化什么」的盘点：第一部分是我逐行读源码盘出的 **10 处细节**，第二部分是并行 agent 架构评审给出的 **3 个大方向**，第三部分给两者的对照与执行顺序。

---

## 一、10 处值得优化的细节（按优先级）

> 优先级 P0（止血/高价值）> P1（地基/清理）> P2（锦上添花）。工程量按人日估算。

### P0 — 高优先级

**1. 子功能失败就杀进程（`process::exit`）**
- 现状：`learn.rs:21`、`update.rs:49`、`refine.rs:105`、`generate.rs:43` 各有 `fatal()` → `process::exit(1)`。REPL 里「学一下这个风格」只要抓取/分析失败，**整个进程直接退出**，违背 v3.1「进程可以死，工作不能丢」的初衷。
- 改法：`run_learn`/`run_update`/`run_refine` 改签名返回 `Result<_, AppError>`，删 4 份 `fatal`。
- 优先级 **P0**｜难度 **低**｜工程量 **0.5 人日**

**2. REPL 本地归档从未发生（`handle_publish` 报「已完成」却没落盘）**
- 现状：`handle_draft_publish` 只做剪贴板 + 网站 MDX，从不写 `outputs/{slug}_v{N}.md`；`handle_publish` 打印「版本管理已完成」但**没有任何版本管理代码**。公众号文章在 REPL 下没有本地 md 原件。
- 改法：补 `next_version` + `write_file` 落盘，改稿（refine/change_style）也写历史版本。
- 优先级 **P0**｜难度 **中**｜工程量 **1 人日**

**3. REPL 缺素材入口（一句话主题当素材，与「不编造」硬约束自相矛盾）**
- 现状：`handle_generate` 把 topic 直接当 idea 传给 `generate_outline`，全文靠一句话主题凭空写。而 `style_system_prompt` 又要求「不添加素材中没有依据的事实」——等于让模型在「禁止编造」下凭空写深度文章。CLI 有素材输入（`inputs/idea_01.md`），REPL 反而没有。
- 改法：扩展 `Generate` 意图支持「参考这份素材/这个链接」，复用 `learn.rs` 的 `fetch_readable_text` 抓 URL。
- 优先级 **P0**｜难度 **中**｜工程量 **1.5–2 人日**

**4. 生成后无风格审查/重写闭环（方案 D）**
- 现状：`render_fulltext` 生成后直接展示，无独立验收。风格遵循度仍靠单次生成运气。
- 改法：正文后加 LLM-as-Judge 审查 → 不合格定向重写 → 再验收，设最大重写次数。
- 优先级 **P0**｜难度 **高**｜工程量 **2–3 人日**

**5. 风格盲评 eval 未固化（评测是一次性的）**
- 现状：本 session 的两条真实 LLM 评测跑完即弃，没有固化成可重复脚本，没有 baseline 数字。
- 改法：3 风格 × 同主题生成 → Claude 盲评风格分类准确率 + 质量清单通过率，固化成 `eval` 脚本。
- 优先级 **P0**｜难度 **中**｜工程量 **1–2 人日**

### P1 — 中优先级

**6. 四份 `md_to_wechat_html`/`env_var` 副本 → 提取 `utils.rs`**
- 现状：`md_to_wechat_html` 在 `repl.rs`/`generate.rs`/`update.rs`/`refine.rs` 各一份，硬编码 `font-size:15px;line-height:2` 排版，改一处漏三处。`env_var`/`fatal` 同样 4 份。
- 改法：新建 `src/utils.rs`（注册进 `lib.rs`），4 模块删副本改 `use`。
- 优先级 **P1**｜难度 **低**｜工程量 **1 人日**

**7. CLI/REPL 双通道生成逻辑重复**
- 现状：`generate_with_outline`（CLI）与 `generate_outline`+`render_fulltext`（REPL）两套编排。prompt builder 已抽，调用编排还重复。
- 改法：CLI 复用 REPL 的 public 函数，收敛成一套。
- 优先级 **P1**｜难度 **中**｜工程量 **1 人日**

**8. 死代码 + 死依赖清理**
- 现状：`clap` 无使用方（CLI 手工解析）；`ModifyOutline` 意图 + `handle_modify_outline`（`#[allow(dead_code)]`）死代码；`AppError::InvalidState` 本 session 换精确报错后已无人构造；`repl.rs:28` 仍留一份 `OUTLINE_SYSTEM_PROMPT` 副本。
- 改法：移除 clap、删死代码、删死变体。
- 优先级 **P1**｜难度 **低**｜工程量 **0.5 人日**

**9. intent 分类 prompt 加 few-shot**
- 现状：`INTENT_CLASSIFY_PROMPT` 纯文字描述，无 few-shot 示例，口语/省略表达的识别靠模型自己悟。
- 改法：加 2–3 个 few-shot（「整一篇/来一篇 = Generate」），实测分类准确率。
- 优先级 **P1**｜难度 **低**｜工程量 **0.5 人日**

### P2 — 低优先级

**10. 轻量日志分级**
- 现状：散落 `println`/`eprintln` + 手写 `[info]/[warn]/[error]` 前缀。
- 改法：引入 `log` + 环境变量控制级别，或自制宏。
- 优先级 **P2**｜难度 **中**｜工程量 **0.5–1 人日**

## 二、3 个迭代大方向（并行 agent 架构评审）

> agent 完整读了项目文档 + 全部源码（含 update/refine/io/clipboard/main/error），以下是基于代码实情的结论。

### 方向一（稳定性）：把「子功能失败就杀进程」改成可恢复的 Result 流
- **命题**：让 REPL 永不因 learn/update/refine 报错而退出，并把 learn 在 REPL 下的交互从 CLI 的 `dialoguer` 阻塞输入改成真正的两阶段对话。
- **为什么**：`dispatch` 直接调 `run_learn`/`run_update`，内部 `process::exit(1)`；且 `run_learn` 用 `dialoguer::Input` 阻塞读 stdin，与 REPL 的 `spawn_blocking` 读 stdin 是**两套互相抢占的输入系统**。另发现 `ARCHITECTURE.md` 声称的 `fetch_and_analyze` 公开函数**实际不存在**，文档描述的能力未实现。
- **涉及**：`learn.rs`/`update.rs`/`refine.rs`/`generate.rs`（去 fatal）、`repl.rs`（dispatch 改造 + 删除风格异步化）、`error.rs`。
- **优先级 高**｜工程量 **2–3 人日**

### 方向二（架构/技术债）：抽取 utils 层，消除副本并移除死依赖
- **命题**：把 4 份 `md_to_wechat_html`/`env_var`/`fatal` 收敛到 `utils.rs`，移除 `clap`，统一两套错误体系。
- **为什么**：复制粘贴漂移——微信排版样式硬编码在 4 处，改字号要改 4 处，漏改产生「REPL 样式 ≠ CLI 样式」的隐性 bug。`error.rs` 的 `InvalidState` 是 dead code，`delete_file`/`StyleSummary.filename` 也是 `#[allow(dead_code)]` 压住的死代码。
- **涉及**：新建 `src/utils.rs`，改 7 个模块，删 clap。
- **优先级 中**｜工程量 **1.5–2 人日**

### 方向三（产品化/交付完整性）：打通「素材输入 → 写作」链路，补全本地归档
- **命题**：REPL 主链路支持多来源素材（URL/文件/粘贴文本）作写作输入，并在生成与改稿后真正落盘 `outputs/{slug}_v{N}.md`，兑现「发布即交付」。
- **为什么**：REPL 主链路缺「素材」头和「归档」腰两段。素材缺失 → 模型只能凭空编，和「不编造素材外事实」的硬约束自相矛盾；本地归档从未发生 → 公众号文章只有易失的剪贴板和网站 MDX 两个去处。`handle_publish` 那句「版本管理已完成」属于**未实现却报了完成**，应优先纠正。
- **涉及**：`repl.rs`（素材读取 + 归档）、`intent.rs`（Generate 扩展素材来源）、`generate.rs`（区分主题/素材）、`io.rs`（复用版本管理）、`learn.rs`（复用抓取）。
- **优先级 高**｜工程量 **3–5 人日**

## 三、10 细节 × 3 方向的对照

| 10 细节 | 归属的大方向 | 关系 |
|---|---|---|
| 1. 去 process::exit | 方向一 | 方向一的主体 |
| 2. 本地归档落盘 | 方向三 | 方向三的「归档腰」 |
| 3. REPL 素材输入 | 方向三 | 方向三的「素材头」 |
| 4. 风格审查重写闭环 | ——（方向之外） | 质量维度的独立增量 |
| 5. eval 固化 | ——（方向之外） | 质量维度的独立增量 |
| 6. 提取 utils.rs | 方向二 | 方向二的主体 |
| 7. 双通道合并 | 方向二（邻近） | 方向二的延伸 |
| 8. 死代码/死依赖清理 | 方向二 | 方向二的一部分 |
| 9. intent 加 few-shot | ——（方向之外） | 质量微调，可顺手做 |
| 10. 日志分级 | ——（方向之外） | 工程卫生 |

**结论**：agent 的 3 个方向覆盖了 10 细节里的 6 条（1/2/3/6/7/8），剩下 4 条（4/5/9/10）是方向之外的质量/工程增量，其中 **4（风格审查）和 5（eval 固化）** 价值最高、且正好对应学习方案 A4。

## 四、建议执行顺序

```
第 1 步  方向一（去 process::exit）        —— 止血，先让 REPL 不再闪退
第 2 步  方向二（utils 层 + 死代码清理）   —— 方向一做完 fatal 副本自然减少，成本更低
第 3 步  方向三（素材输入 + 本地归档）     —— 工程量最大，依赖方向一的抓取复用 + 方向二的工具函数
并行穿插  细节 5（eval 固化）+ 4（风格审查） —— 质量线，独立于三方向，按学习方案 A4 节奏推进
顺手做    细节 9（few-shot）+ 10（日志）     —— 各 0.5 人日，碎片时间可清
```

一句话：**先止血（方向一）→ 再清地基（方向二）→ 最后补交付（方向三），质量线（eval + 审查）独立并行推进。**
