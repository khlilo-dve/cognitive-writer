# 写作风格遵循度改进设计

## 状态

设计文档，仅供评审和后续实现使用。本次不执行源码修改，不改变当前生成行为。

## 目标

提升生成文章对用户提供写作风格的稳定遵循程度，使系统不只是复用少量口语词或 Markdown 排版，而是能够复用目标风格的：

- 破题方式；
- 核心判断与论证动作；
- 段落节奏与句式；
- 语气、人称和词汇偏好；
- 结尾收束方式。

## 非目标

本设计不包含以下内容：

- 本地 `outputs/` 归档问题；
- LLM provider、模型或 API 协议更换；
- 生成文章主题和素材提取逻辑重构；
- 立即执行任何源码、风格文件或提示词修改；
- 一开始就引入 JSON Schema、数据库或新的持久化系统。

## 一、现状与问题定位

### 当前生成链路

当前系统的主要生成链路是：

```text
主题 + 素材
    ↓
通用大纲提示词（不接收风格）
    ↓
通用大纲
    ↓
完整 styles/{name}.md 作为正文 system prompt
    ↓
正文
```

代码位置：

- `src/repl.rs:527-560`：匹配风格、生成大纲；
- `src/generate.rs:50-58`：通用大纲 system prompt；
- `src/generate.rs:77-95`：正文渲染；
- `src/repl.rs:566-606`：把风格、 大纲和主题传入正文渲染。

### 根因

#### 1. 风格文件混合了分析资料和执行指令

`styles/*.md` 可能同时包含：

- 抓取页面的说明或残留内容；
- 风格分析报告；
- 原文示例及解析；
- 风格复刻指令；
- 排版要求和去 AI 味规则。

生成模型需要自行判断哪些内容是背景资料、哪些内容是硬约束。输入噪音会稀释真正的执行指令。

#### 2. 大纲阶段没有风格约束

大纲生成只接收素材，不接收风格。因此风格无法影响：

- 文章从什么角度破题；
- 核心判断的组织方式；
- 论证的递进、转折和反例排除；
- 小标题的风格；
- 结尾的收束方式。

正文阶段只能在既定结构上模仿表达，容易形成“通用文章结构 + 少量风格表面特征”。

#### 3. 风格规则可能互相冲突

以当前 `styles/qingbian.md` 为例，存在类似冲突：

- 前文要求频繁使用设问，后文又限制全文反问句数量；
- 前文强调频繁使用“你”，后文又要求以“我”为主视角；
- 分析报告中的描述性结论、原文示例与执行规则混在一起。

如果不先统一规则，单纯改调用方式不会稳定解决问题。

#### 4. 缺少生成后的风格验收

当前文章生成后直接展示，没有独立判断：

- 是否使用了目标风格的破题方式；
- 是否遵循了目标风格的论证动作；
- 是否出现冲突规则或明显 AI 模板；
- 是否需要定向重写。

因此风格遵循度只能依赖一次生成的偶然结果。

### 当前输出的判断标准

风格遵循不应只看是否出现几个相似词，而应至少分为四层：

1. **结构层**：文章的破题、论证顺序、章节组织、结尾是否符合风格；
2. **论证层**：是否复用了目标风格的判断方式、反例处理和推进动作；
3. **表达层**：句式、段落长度、语气、人称、词汇是否符合；
4. **排版层**：标题层级、加粗、引用块、段落空行等是否符合。

结构层和论证层优先级高于表达层和排版层。

## 二、候选方案

### 方案 A：清洗风格文件，只注入执行指令

#### 设计

把风格文件的内容职责分开：

- 分析报告供人阅读；
- 风格复刻指令供生成模型执行。

生成时只读取“风格执行指令”部分，不再把抓取说明、分析过程和大段解释全部注入正文 system prompt。

建议执行指令至少包含：

```markdown
## 风格定位
## 破题方式
## 结构与论证
## 段落与句式
## 语气与人称
## 用词偏好
## 结尾策略
## 排版要求
## 禁止事项
```

正文调用的提示词需要明确：

- 该内容是必须执行的写作约束；
- 只输出 Markdown 正文；
- 不复述规则和写作过程；
- 不添加素材没有依据的事实、数据或人物观点；
- 规则冲突时遵循明确的优先级。

#### 优点

- 改动最小；
- 能立即减少输入噪音；
- 不增加 LLM 调用次数；
- 适合快速验证“风格文件污染”是否是主要问题。

#### 缺点

- 大纲阶段仍不受风格约束；
- 风格不能充分影响文章结构；
- 依赖人工清洗和维护执行指令。

#### 适用场景

作为低成本第一步，或用于快速诊断问题。

### 方案 B：风格同时注入大纲和正文

#### 设计

将生成链路改为：

```text
素材 + 风格执行指令
          ↓
      风格化大纲
          ↓
风格执行指令 + 风格化大纲 + 素材
          ↓
        正文
```

大纲提示词需要要求：

1. 先确定符合目标风格的核心判断；
2. 设计符合目标风格的开头破题；
3. 每个章节说明核心判断、论证动作、素材使用方向和衔接关系；
4. 标明需要排除的常见误解或错误路径；
5. 设计符合目标风格的结尾；
6. 避免默认套用“背景—问题—原因—建议—总结”模板；
7. 只输出大纲，不写正文。

正文提示词需要同时接收：

- 风格执行指令；
- 风格化大纲；
- 原始素材。

正文生成前要求模型内部检查：

- 开头是否符合风格破题方式；
- 每节是否只有一个核心判断；
- 论证动作是否符合目标风格；
- 句式与段落节奏是否符合；
- 结尾是否符合目标风格；
- 是否出现 AI 模板句或素材外事实。

模型只输出正文，不输出检查过程。

#### 优点

- 解决当前最核心的结构问题；
- 风格可以影响角度、论证顺序、小标题和结尾；
- 不要求立即改变风格文件存储格式；
- 改动范围可控，适合当前代码架构。

#### 缺点

- 风格指令在两个阶段重复注入；
- Prompt 变长；
- 风格文件冲突会在两个阶段被放大；
- 没有独立验收，仍可能有生成波动。

#### 适用场景

作为当前系统的正式第一版改造。

### 方案 C：结构化风格协议

#### 设计

把自然语言风格报告转换成结构化的 Style Profile，再由大纲和正文生成器读取。

概念结构：

```json
{
  "identity": "理性分析型、反直觉、通俗白话",
  "opening": {
    "strategy": "直接抛出反直觉判断",
    "avoid": ["故事铺垫", "背景寒暄"]
  },
  "structure": {
    "preferred": ["核心判断", "拆解机制", "排除误解", "现实收口"],
    "avoid": ["背景—问题—原因—建议模板"]
  },
  "paragraph": {
    "length": "短段为主",
    "sentences_per_paragraph": "2-5"
  },
  "rhetoric": [
    "设问后自答",
    "短句打断长逻辑",
    "否定式推进",
    "破折号强调"
  ],
  "tone": ["冷静", "轻微讽刺", "现实主义"],
  "vocabulary": {
    "prefer": ["口语词", "具体数字", "精确术语"],
    "avoid": ["空泛励志词", "标准化总结句"]
  },
  "ending": {
    "strategy": "现实承认与智慧收束",
    "avoid": ["行动号召", "鸡汤升华"]
  }
}
```

风格学习流程需要输出并校验该协议；旧 Markdown 风格文件需要兼容读取或迁移。

#### 优点

- 减少自然语言报告歧义；
- 字段可以逐项校验；
- 便于多个风格长期维护和比较；
- 后续可增加风格强度和自动验收规则。

#### 缺点

- 改造范围最大；
- 需要重做风格学习输出和解析；
- 需要设计旧风格文件兼容策略；
- 结构化字段仍然需要自然语言提示词转译，不能保证单独解决模型执行问题。

#### 适用场景

风格库成为长期核心能力、风格数量持续增长时。

### 方案 D：生成后风格审查与自动重写

#### 设计

在正文生成后增加审查闭环：

```text
风格化大纲 → 正文 → 风格审查
                       ├─ 合格 → 输出
                       └─ 不合格 → 按审查意见重写 → 再验收
```

审查模型只输出结构化结果，至少包含：

```json
{
  "score": 0,
  "passed": false,
  "violations": [
    {
      "rule": "段落节奏",
      "evidence": "具体原文片段",
      "suggestion": "具体修改建议"
    }
  ],
  "must_rewrite": ["开头没有形成反直觉破题"]
}
```

重写阶段必须保持：

- 原主题不变；
- 原始素材事实不变；
- 核心论点不被审查意见之外的修改破坏；
- 只修复已识别的风格问题。

需要设置最大重写次数，避免循环调用。

#### 优点

- 提供明确的质量闭环；
- 能暴露具体违规位置；
- 风格复杂时稳定性最高。

#### 缺点

- 增加调用次数、延迟和成本；
- 审查模型可能误判；
- 需要处理 JSON 解析、审查失败和重写失败；
- 如果风格规则冲突，审查结果会不稳定。

#### 适用场景

文章质量优先于调用成本，或需要高质量模式时。

|---|---:|---:|---:|---:|---|
| A. 清洗执行指令 | 低 | 低 | 中 | 0 | 快速修复/诊断 |

## 四、推荐路线

采用分阶段路线，而不是一次性重构：

```text
阶段 1：A + B
    清洗执行指令
    风格同时注入大纲和正文

阶段 2：D
    正文生成后增加风格审查
    仅对不合格稿件触发定向重写

阶段 3：C
    风格数量和维护成本达到阈值后，演进为结构化协议
```

### 推荐原因

- 阶段 1 直接处理当前最确定的两个根因：输入噪音和大纲无风格；
- 不改变 LLM provider 和整体双通道架构；
- 阶段 2 增加质量闭环，但只在必要时增加调用成本；
- 阶段 3 留给真实使用反馈，避免过早设计结构化协议。

### 阶段 1 的推荐优先级

在 A + B 内部，先做以下顺序：

1. 统一现有风格文件中的冲突规则；
2. 明确“分析报告”和“执行指令”的边界；
3. 让大纲生成接收执行指令；
4. 让正文生成只接收执行指令、风格化大纲和素材；
5. 增加提示词中的事实边界和内部自检要求；
6. 用同一主题分别生成多次，对风格遵循度进行人工对比。

## 五、`qingbian` 风格的规则统一建议

在任何实现前，先把冲突规则收敛为一份明确指令。建议基线如下：

### 风格定位

- 理性分析 + 反直觉论证 + 通俗白话；
- 像一个懂得多、愿意说真话的老朋友；
- 冷静、有力度，允许轻微讽刺；
- 不煽情，不做空泛鸡汤。

### 视角与人称

- 以第二人称“你”作为主要读者视角；
- 只有在讲述个人经历或判断来源时使用“我”；
- 不使用“我们”制造虚假共识。

### 结构与论证

- 开头直接抛出一个反直觉判断，不用故事铺垫；
- 每个章节只围绕一个核心判断；
- 先提出常见误解，再拆解其错误；
- 优先使用阶段化分析、机制拆解、反例排除和现实推演；
- 避免默认套用“背景—问题—原因—建议—总结”模板；
- 结尾回到现实限制或判断，不做泛泛行动号召。

### 句式与节奏

- 短段为主，长短句交替；
- 允许段落只有一句话；
- 使用短句打断长逻辑；
- 破折号可用于转折或强调，但不机械重复；
- 全文反问句不超过 2 句，只用于关键认知冲突；
- 不在每个段落重复“为什么……因为……”结构。

### 词汇与事实

- 使用具体数字、场景和人物替代空泛概括；
- 允许适度口语词和精确书面词并存；
- 不添加素材中没有依据的事实、数据、实验结果或名人观点；
- 无法确认来源时，改为一般性表达，不伪造精确数字。

### 禁止事项

- 禁用标准化 AI 套话和空泛升华；
- 禁止三段排比后强行总结；
- 禁止每段都以金句或感叹号收尾；
- 禁止为了模仿风格而堆砌口语词、破折号或反问句；
- 禁止复述提示词、输出自检过程或解释写作步骤。

## 七、验收标准（后续实现时使用）

### 功能验收

- 大纲生成调用能够接收到清晰的风格执行指令；
- 正文生成只接收清洗后的风格执行指令，不接收无关抓取和分析噪音；
- 风格规则不再存在相互冲突的硬约束；
- 生成提示词明确禁止素材外事实和写作过程输出。

### 质量验收

使用同一主题至少生成 3 篇，人工逐项检查：

1. 开头破题方式；
2. 核心论证动作；
3. 段落节奏；
4. 句式与人称；
5. 语气与词汇；
6. 结尾收束；
7. AI 模板句和事实幻觉。

最低标准：7 项中至少 5 项稳定符合，且不得出现明显素材外的精确事实、数据或人物引用。

### 工程验收

- `cargo test --lib` 全部通过；
- 生成 prompt 的单元测试覆盖风格内容确实传入大纲和正文；
- 不使用全局 `allow(dead_code)` 或静默忽略错误；
- 不改变当前 CLI 与 REPL 的既有入口约定。
