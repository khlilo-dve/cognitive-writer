## 3. 为什么建议 30–60 元而不是承诺 23 元

- 基准：约 23.02 元。
- 输出量翻倍而输入不变：约 33.92 元。
- 在上一项基础上再增加 50% 调用/长度余量：约 50.88 元。
- 因此首轮用 30–60 元作为计划区间，100 元作为建议硬上限；额外空间覆盖一次有明确原因的受控修订，不能视为要求花完。

假如 P1 实测远超假设，先完成费用重估再扩展任务。100 元不是当前已获授权额度。用户接受总额后，执行者可以在总额与既定范围内按阶段自主运行，不逐请求询问。

## 4. 预算控制实现要求

现有 `llm.rs` 没有保存 usage，故预算控制是 P1 的前置工作，不能等跑完才估。

每次请求记录 role/model、输入/输出/缓存/推理 usage（按服务端实际提供字段）、预计费用、实际可计费费用、时间、请求身份、缓存命中和错误。推理 token 若已经包含在 completion_tokens 中，不重复计费。

- 请求前按估计输入和已验证输出上限预留费用，并把正在执行的并发请求预留额计入总占用；未知输入用保守上界，不能把汉字数直接当 token 精确值。
- 返回后用 usage 对账；未返回 usage、超时和运输失败可能仍收费，不能按零元处理，保留不确定费用预留。
- 每轮最多 3 个并发模型请求，所有角色共用一个预算账本。
- 已花 + 在途预留 + 下一请求上界超过批准总额时，不再发起请求，先保存进度。
- 剩余额度不够下一完整阶段时，给出已完成成果、剩余范围和新估算；不得在无说明情况下降低样本数后宣称完整研究。
- 缓存复跑必须零新模型请求；模型、Prompt、JSON 模式或参数改变会使相应缓存失效。
- 80% 额度时更新预计剩余成本；不需要用户决定的情况下只做通知。批准额用完前停止，追加需用户明确同意。

API 端预算是基于 usage/预留的执行控制，不是对第三方账单的无条件保证。费用渠道或输出限制无法核验时，不启动大批量实验。
