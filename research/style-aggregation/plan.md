## 1. 目标与不变边界

中心问题：多文章聚合是否提高风格表示的可靠性，同时保留作者辨识度，并在新主题写作中有效？

分别回答四个问题，不合成采用总分：

1. 同作者单篇 Style 是否比不同作者更相似？
2. 聚合是否减少单篇偶然性，同时避免变成通用写作建议？
3. 1 / 2 / 3 / 5 / 7 / 10 篇时，哪些维度稳定，哪些仍变化？
4. 同一 Flash Writer 使用聚合 Style 后，新主题风格表现是否改善？

研究成功意味着得到可信答案，不要求聚合一定胜出。技术跑通、作者风格假设成立、生成改善、用户盲测支持是不同状态。

不引入 LangGraph、不迁移 Python 主程序、不建通用 Graph Runtime、不做 Multi-Agent、不重写 REPL、不做云服务或 UI、不将内容质量优化替换为主线。不自动改正式学习默认值、不覆盖 `styles/`，研究完成后另行讨论产品采用。

## 2. 已核对的项目基础

基于规划前 Git HEAD `9cf87b0` 与当前源码：

- `learn.rs` 默认 `direct_free`，自由 Markdown 进入正式风格库；`style_learning.rs` 已有有界修复及可注入调用接口。
- `styles.rs` 保存 Markdown；不存在统一解析全部风格的 StyleSpec 结构体。两阶段 `Feature / Analysis` 不能冒充现行默认输出 Schema。
- `generate.rs` 有共用的大纲、正文提示词，可复用 Writer，不改生成包装。
- `eval_store.rs` 有请求身份、冻结输入和检查点，但一个 Store 绑定一个模型，默认输出到 `eval/runs/`。
- `llm.rs` 当前仅解析正文响应，没有保存 usage。这是分层模型和费用控制必须补齐的最小工程缺口。
- Transfer v2 已有五维独立评估；现有入口仍带旧样本与任务假设，复用语义和校验器，不能照搬固定样本加载器。

## 4. 模型分工

| 职责 | 固定模型/执行方式 | 理由 |
|---|---|---|
| 单篇风格提取、比较视图、语义匹配 | `mimo-v2.6-pro` | 需要分开内容、表达和条件，属于困难判断 |
| 特征归并、冲突核验、Profile 与执行文本编译 | `mimo-v2.6-pro` | 错误会影响所有后续生成 |
| 风格保真、原文独立、作者匹配与疑难复核 | `mimo-v2.6-pro` | 统一裁判，保留同模型偏差限制 |
| 大纲与正文 | `mimo-v2.6-flash` | A/B 全部保持同一 Writer，降低成本且接近日常使用 |
| 可选低风险摘要/字段建议 | `mimo-v2.6-flash` | 不决定研究结论；优先模板直接完成 |
| 计数、哈希、划分、矩阵、图表、同步、费用 | Rust/脚本 | 不调用模型 |

固定的是每种职责的模型配置，不是全流程只用一个模型。不得在某篇难写时临时换 Pro，再把结果混入 Flash 组。模型降级或路由变化必须新分组、新版本。模型 ID、请求参数、返回模型、Prompt 哈希、JSON 模式均进入 provenance；服务端未提供版本号则明确未知。

研究入口接收显式 model role 与输出目录，不修改 `.env`。保留旧公开接口；增加研究需要的响应元数据和受支持的输出上限。确认官方接口接受哪些参数后再冻结，不能把未发送的 temperature/seed 当已控制变量。输出 token 预算包含可能的推理消耗，计费以实际 usage 和账单为准。

## 5. 最小架构调整

拟新增以下职责模块，命名可在实现时微调，单模块遵守 500 行约束：

- `style_profile`：研究特征、支持/反例、执行规则及 Schema 版本。
- `style_compare`：匹配结构校验、重合/冲突/覆盖率的确定性计算。
- `style_aggregate`：最小上下文、语义归并、按文章去重计数、编译。
- `research_dataset`：manifest、划分、哈希、来源和输入清洗。
- `research_run`：阶段依赖、任务状态、预算预留、断点恢复。
- `research_report`：分项汇总和绘图数据；图像输出工具按实际环境选择。

研究命令作为薄入口，依次支持准备、单阶段运行、恢复、报告与飞书同步；不让 CLI 自己承载领域逻辑。接口细节在 P1 先写进运行说明再实施。

State 只持有数据版本、任务状态、产物引用、错误和预算账本。各步骤只拿需要的 Context；单篇提取只见当前文章，聚合只见当前子集，生成只见执行 Style 与主题素材，作者匹配不见方法标签和支持频率。

复用 Store 的传输与校验，扩展多模型明确请求身份和可配置输出根。成功响应、语义无效输出、运输失败、修复响应分开记录。失败仅阻断依赖链，其他独立任务继续；网络重试沿用有界规则，格式修复最多一次，不自动循环调 Prompt。

## 6. 结果与过程记录纪律

每个非平凡实验、失败和突破都必须有 `event_id`、时间、run、问题、改变、结果、证据、费用、下一步。写入 [journal.md](journal.md)，并同步飞书 Journal。详细数据在 run 中，日志用通俗语言解释。

- 正向结果标记为“发现”，经固定条件复测或独立确认后才能称为“得到支持”。
- 工程失败、评测无效和研究假设不成立分开标记。
- 不删除失败 run、不隐去反例、不把解析失败填成 0 分或通过。
- 方法、阈值、样本、Prompt、模型变化都记录原因和影响，不合并不同版本统计。
- 阶段报告前半页固定回答：想知道什么、做了什么、看到了什么、意味着什么、还不能说明什么、下一步和已花费用。
- 每张图有一句中文结论、样本数、单位、run、数据源和方法版本。小样本图展示原始点或范围，避免只有均值。

## 7. 验证与提交

测试重点：样本隔离、按文章计数、缺失不当反例、合法未知状态、相似度对称与边界、模型身份与缓存失效、文件恢复、预算并发预留、usage 缺失、飞书重复同步与响应回读。使用 tempfile 和本地模型桩，不写脆弱的 LLM 字符串快照测试。

每次代码变动后跑 `cargo test --lib`，新增入口构建与相应回归；触及交互流程时运行相关终端脚本。文档检查链接与数字一致性。检查 `git diff`，定向 add/commit，不 push。新模块在 `src/lib.rs` 注册；错误使用 AppError。阶段收尾删除本次无用临时文件，保留全部研究证据。

## 8. 偏航检查与停止条件

每个主要变更先问：它回答哪个研究问题？是否需要新增模型调用？能否单独重跑？失败留下什么证据？是否在修与研究无关的历史债务？

下列情况停止相关在线阶段并写报告：预算不足；usage/账单无法建立可靠估算上界；输入泄漏；引用校验持续失败；样本来源不可靠；固定对照明显失效。无显著改善本身不停止写负面报告。

2026-10-07用户明确授权：依据最初实验目标自主制定方案，遇到挫折、失败或问题，自行提出改进并执行，无需确认。此授权取代此前“最多一次受控方法修订”的限制。每次修订仍须先登记具体问题、改变、开发样本、验证条件和单次费用上限；保留旧版本，不能更换门槛来制造正面结论。100元总预算保持，确认集隔离保持。

最终 confirmation 解封以后，不再将其用作调参集；需要新确认实验则另建留出并在原总预算内安排。延后新增作者、embedding 服务、生产集成和大规模用户研究。
