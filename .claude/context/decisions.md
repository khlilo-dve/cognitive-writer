# 核心架构决策与技术债 (decisions.md)

## 核心架构决策 (Architecture Decision Records)

### ADR-1: 为什么采用纯 Rust 本地原生实现？
- **背景**: 写作工具往往被做成 Web 界面或 Python 脚本。
- **决策**: 使用 Rust 构建静态编译的终端 REPL 工具。
- **原因**:
  1. 极低资源开销与毫秒级启动，可作为本地长驻守工具；
  2. 强类型系统与编译期检查，保证复杂状态机和 I/O 交互零意外崩溃；
  3. 便于本地直接无缝操作操作系统剪贴板与原生文件树。

### ADR-2: 为什么将生成过程拆为“大纲 + 正文”两阶段？
- **背景**: 直接将用户主题送入模型写全文，长文本容易偏离预期且纠错成本极高。
- **当前实现**: 保留大纲和正文两次模型调用，生成后自动衔接正文，用户审阅正文。`WaitingForOutline` 枚举尚存，但常规流程不进入；旧会话恢复到该状态的处理待完善。
- **原因**: 先组织结构再展开正文，减少结构层跑题；是否恢复人工大纲检查点是产品选择，不能由过期文档推定。

### ADR-3: 为什么将风格规范化为“可执行 Spec”？
- **背景**: 传纯提示词让模型自由发挥经常失效。
- **当前实现**: 风格是含十个二级标题的 Markdown 文本，整份注入大纲和正文 Prompt；代码中没有名为 `StyleSpec` 的结构体。
- **原因**: 负向约束（Negative Constraints）和明确的结构范式极大抑制了通用大模型的默认客套腔调。

## 已知技术债与优化路径

1. **REPL 下 `run_learn` 阻塞冲突**:
   - **现象**: 在 REPL 异步主循环中调用 `learn` 时，使用了 `dialoguer` 进行阻塞式命名输入，与 tokio 的异步调度存在潜在冲突。
   - **拟优化方案**: 重构为两阶段自然语言对话式交互，由状态机统一接收命名。
2. **`handle_delete_style` 中的同步 I/O**:
   - **现象**: 风格删除函数中仍然包含同步的 `stdin.read_line()`。
   - **拟优化方案**: 改写为异步读取或由意图解析器在前面直接捕获参数。
3. **CLI 与 REPL 的生成逻辑重复（2026-09-05 已解决）**:
   - CLI 已复用 `generate_outline` / `render_fulltext`，保留 CLI 的进度提示。
4. **待方案确认**：REPL 单一输入通道、公开 String 错误迁移、intent/styles 规模治理。具体边界与验收见 `.claude/tasks/plan.md`。
